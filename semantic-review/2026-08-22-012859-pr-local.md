# Staff-scoped Veepee administration

The change introduces a `staff` role, provisions it through administrator-only endpoints, and splits the admin API into operational and administrator-only capabilities. Staff receives the dashboard summary, catalogue reads, non-delete brand/category maintenance, order fulfilment, negotiation response, and customer reads; price management, payments, marketing, settings, reviews, affiliate tools, upgrades, and staff administration remain administrator-only in the new route matrix. The admin client mirrors that boundary with role-filtered navigation, direct-path denial, nested active states, a responsive Veepee shell, and a login that accepts only administrator or staff accounts. **Watch for: [Medium, confirmed]** two generic authenticated `/auth` endpoints still let staff enter customer upgrade and notification flows, and a staff password reset leaves existing refresh sessions usable.  
**Verdict**: NEEDS_CHANGES

## High-level view

The permission model is now expressed at the API boundary rather than relying on navigation concealment. `operationsStaff` is applied only to the approved operational endpoints, while the sensitive administration surface uses an administrator-only guard; the client independently filters navigation and renders a restricted state for direct staff navigation to a protected page.

The category, brand, and upload changes preserve non-delete maintenance for staff, while the route audit excludes staff from customer commerce, payment, Razorpay, negotiation-as-customer, notification, product mutation, and administrator-only tool routes. The remaining gap is in the generic authenticated profile surface: it was not included in the role matrix and can still be used to start an upgrade request or register a notification token.

Staff deactivation revokes refresh tokens and every protected request rechecks `isActive`. Password changes do not take the same revocation path, leaving a previously issued refresh token valid after an administrator resets the password.

## Customer self-service routes bypass the staff capability boundary

**[Medium, confirmed]** The new staff role is excluded from the customer commerce, payment, Razorpay, notification, and order routes, but `src/routes/authRoutes.js` leaves `POST /auth/convert-to-wholesaler` and `POST /auth/fcm-token` behind generic `protect` only. A staff token can therefore submit a wholesaler-conversion request and write business details, contact information, and pending-verification state through `src/controllers/authController.js`; it can also register an FCM device token through the same controller.

The conversion handler does not immediately change the account role, but it creates a pending customer-upgrade workflow on a staff account; the new administrator customer query deliberately excludes staff, making that request harder to administer through the intended upgrade surface. Apply an explicit customer/admin role guard to the two endpoints, with staff rejected before either controller mutates the account.

## Staff password resets do not invalidate existing refresh sessions

**[Medium, confirmed]** `src/controllers/admin/staffController.js` hashes and saves a supplied password, but refresh tokens are revoked only when `isActive` changes from true to false. The revised refresh endpoint validates that the account is active, so an unchanged active account can continue using an already-issued refresh token to obtain new access tokens after its password has been reset.

Password reset is normally used to contain a compromised credential or end a departing employee’s access. Revoke all unrevoked `RefreshToken` records when `password` is supplied, ideally in the same update flow as the password write; deactivation already demonstrates the required token invalidation behavior.

## Role-boundary changes have no runnable coverage

**[Low, confirmed]** Neither worktree adds a staff/RBAC/session test. This leaves the large allow/deny matrix across `adminRoutes`, the non-admin routes, direct dashboard URLs, and refresh/session behavior unprotected from future guard changes.

`npm run build` in `Veepee-admin` succeeds. `npm test` in `Veepee-backend` does not execute its inventory cases because test setup attempts to create a `User` without the required `authProvider`; the `User` model and test fixture are outside this diff, but the failure prevents validation of the changed backend in its current state. Add focused route tests and repair the fixture before relying on the suite for authorization regressions.
